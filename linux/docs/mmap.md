# mmap：从虚拟地址到共享 page cache

`mmap`（memory map，内存映射）的本质是：

> 在进程的虚拟地址空间中建立一段映射，让一段虚拟地址与文件中的某一段内容关联起来。之后读写这段地址，就相当于读写文件对应的位置。

它不是“把整个文件复制进内存”，也不是“绕过磁盘”。它主要告诉操作系统：

```text
虚拟地址 base + n  <->  文件 offset + n
```

如果没有访问某一页，操作系统通常不需要把对应文件内容读入物理内存。

## 1. 前置概念：虚拟内存

程序中看到的地址通常不是物理内存地址，而是当前进程自己的虚拟地址：

```text
进程虚拟地址
0x1000 --+
0x2000   |  由页表映射
0x3000 --+
             |
             v
        物理内存页
```

操作系统以“页”为单位管理映射，常见页大小是 4 KiB。每个进程都有自己的虚拟地址空间和页表，因此相同的虚拟地址在不同进程中可以指向不同的物理页，不同的虚拟地址也可以指向同一个物理页。

普通内存可以映射到匿名物理页；`mmap` 还可以让虚拟页与文件内容关联。

## 2. mmap 一个文件时发生了什么

假设有一个 1 GiB 文件：

```c
char *p = mmap(NULL, file_size, PROT_READ, MAP_SHARED, fd, 0);
```

调用成功后，操作系统通常不会立刻读取这 1 GiB 文件，也不会立即分配 1 GiB 物理内存。它先在进程的虚拟地址空间中记录映射关系：

```text
进程虚拟地址范围              文件范围
p + 0       ----------------> offset 0
p + 4096    ----------------> offset 4096
p + 8192    ----------------> offset 8192
...
```

这时执行：

```c
char value = p[8192];
```

CPU 会像读取普通内存一样访问 `p + 8192`。

如果对应页面还没有进入物理内存，就会发生缺页异常（page fault）：

1. CPU 发现该虚拟页暂时没有有效的页表项。
2. CPU 暂停当前指令并进入内核。
3. 内核根据映射记录，找到该地址对应的文件位置。
4. 如果文件页已经在 page cache 中，内核直接建立页表映射。
5. 否则，内核从存储设备读取对应页面到 page cache，再建立映射。
6. CPU 返回用户态，重新执行刚才的读取指令。

整个过程可以简化为：

```text
第一次访问

CPU 访问虚拟地址
        |
        v
    缺页异常
        |
        v
读取文件页，或复用已有 page cache 页
        |
        v
    建立页表项
        |
        v
重新执行原来的内存访问


后续访问

CPU 访问虚拟地址
        |
        v
通过页表直接访问物理内存
```

因此，`mmap` 建立的是地址关系；真正的数据加载通常发生在访问页面时。

## 3. page cache 在哪里

文件 I/O 通常经过操作系统的 page cache。它是物理内存中对文件内容的缓存：

```text
存储设备上的文件
        |
        v
物理内存中的 page cache 页
```

`mmap` 并不是让 CPU 直接访问磁盘。进程最终访问的仍然是物理内存中的页面，只是内核知道这些页面对应哪个文件和哪个文件偏移量：

```text
进程虚拟地址
      |
      | 页表
      v
page cache 物理页
      |
      | 该页对应文件的某个区间
      v
存储设备上的文件
```

## 4. mmap 与 read 的区别

传统 `read`：

```c
read(fd, buffer, size);
```

常见的数据路径是：

```text
文件 -> page cache -> 用户提供的 buffer
```

程序最终操作自己的 `buffer`。即使文件内容已经进入 page cache，`read` 通常仍要把数据复制到用户缓冲区。

`mmap` 的路径是：

```text
文件 -> page cache
             ^
             |
       映射到进程虚拟地址
```

程序通过映射地址直接访问 page cache 中的文件页，通常不需要再复制到单独的用户缓冲区。

因此，`mmap` 的关键不是“文件直接变成内存”，而是：

> 让文件页直接成为进程虚拟地址空间的一部分。

## 5. mmap 为什么可能更快

`mmap` 可能减少：

- `read()`、`write()` 系统调用次数；
- page cache 到用户缓冲区的数据复制；
- 应用自己维护大块缓冲区的代码；
- 随机访问文件时的定位和读取操作。

例如，要访问文件第 500 MiB 位置的一个字节，可以直接按地址偏移访问：

```c
char value = mapping[500 * 1024 * 1024];
```

程序不需要循环读取前面的内容。

但 `mmap` 不保证更快：

- 首次访问仍然可能产生存储 I/O；
- 大量随机访问会产生许多缺页异常；
- 映射远大于可用内存时，仍然可能出现页面回收和反复读取；
- 顺序读取场景中，`read` 配合内核预读可能同样高效；
- 缺页成本隐藏在普通内存访问中，延迟更难显式控制和统计。

所以，“`mmap` 是零拷贝，因此一定更快”并不准确。

## 6. mmap 写文件是什么意思

如果映射允许写，程序可以像修改数组一样修改映射：

```c
p[0] = 'A';
```

CPU 首先修改对应的物理内存页，该页面随后被内核标记为脏页。

### 6.1 `MAP_SHARED`

`MAP_SHARED` 使用共享映射：

```text
修改映射内存
      |
      v
修改共享的 page cache 页
      |
      v
内核稍后把脏页写回文件
```

其他映射同一文件区域的进程也可以看到这份修改。并发读写时，应用仍然需要锁、原子操作或其他进程间同步手段来约束访问顺序。

可以使用 `msync()` 请求同步映射内容，但“修改了内存”“进入操作系统缓存”和“持久化到存储设备”不是完全相同的时刻，具体保证还取决于调用参数、文件系统和平台。

### 6.2 `MAP_PRIVATE`

`MAP_PRIVATE` 是私有的写时复制（copy-on-write）映射：

```text
读取：可以使用原文件的 page cache 页
写入：复制出当前进程自己的私有页面
```

写入私有页面不会修改原文件，其他进程也看不到这份私有修改。

## 7. 两个进程怎样共享同一个 page cache 页

关键点是：

> 两个进程并不是共享虚拟地址，而是各自的页表可以把不同虚拟地址翻译到同一个 page cache 物理页。

假设文件 `data.bin` 的前 4 KiB 内容是：

```text
Hello...
```

进程 A 和进程 B 都使用 `MAP_SHARED` 映射这 4 KiB：

```text
进程 A 中，mmap 返回：0x70000000
进程 B 中，mmap 返回：0x50000000
```

地址不同，但操作系统可以这样设置两个进程的页表：

```text
进程 A                         物理内存
虚拟地址 0x70000000 --页表 A--+
                              +--> 物理页 #42："Hello..."
进程 B                         |
虚拟地址 0x50000000 --页表 B--+
```

物理页 `#42` 是 page cache 中缓存的 `data.bin` 第 0～4095 字节。完整关系是：

```text
进程 A 的虚拟地址 0x70000000
                |
                | 页表 A
                v
        page cache 物理页 #42
                ^
                | 页表 B
                |
进程 B 的虚拟地址 0x50000000

物理页 #42 对应 data.bin 的第 0～4095 字节
                |
                v
         内核稍后写回磁盘文件
```

每个进程都有自己的页表。CPU 访问虚拟地址时，使用当前进程的页表转换地址：

```text
进程 A：0x70000000 -> 页表 A -> 物理页 #42
进程 B：0x50000000 -> 页表 B -> 物理页 #42
```

虚拟地址不需要相同。只要最终翻译出的物理页相同，两个进程访问的就是同一批字节。可以把它理解成两个不同的入口指向同一个对象：

```text
A 的入口：0x70000000 --+
                        +--> 同一个物理页
B 的入口：0x50000000 --+
```

### 7.1 映射如何形成共享

假设 A 先访问映射：

```text
A 访问 0x70000000
        |
        v
发生缺页异常
        |
        v
内核读取 data.bin 的前 4 KiB
        |
        v
内容进入 page cache 物理页 #42
        |
        v
页表 A 指向物理页 #42
```

之后 B 访问自己的映射：

```text
B 访问 0x50000000
        |
        v
发生缺页异常
        |
        v
内核发现对应文件页已经在 page cache 中
        |
        v
不必再次读取存储设备
        |
        v
页表 B 也指向物理页 #42
```

最终形成：

```text
页表 A --+
          +--> 物理页 #42
页表 B --+
```

### 7.2 A 修改后，B 为什么能看到

假设物理页内容是：

```text
Hello
```

进程 A 执行：

```c
a[0] = 'Y';
```

因为使用 `MAP_SHARED`，A 修改的是共享物理页：

```text
物理页 #42：Hello -> Yello
```

进程 B 通过自己的虚拟地址读取时，页表仍然指向物理页 `#42`，所以它读到的也是：

```text
Yello
```

随后这页会被标记为脏页：

```text
A 修改内存
    |
    v
共享 page cache 页变成 "Yello"
    |
    +--> B 可以通过自己的映射看到 "Yello"
    |
    v
内核稍后把脏页写回 data.bin
```

两个进程共享的是内存中的 page cache 页，而不是“同时直接访问磁盘”。

### 7.3 换成 `MAP_PRIVATE` 会怎样

`MAP_PRIVATE` 在还没有写入时，也可能让两个进程读取同一个 page cache 页：

```text
页表 A --+
          +--> 文件页 #42："Hello"
页表 B --+
```

但是 A 一旦写入，就会触发写时复制：

```text
写入前：

A --+
    +--> 文件页 #42："Hello"
B --+

写入后：

A ------> 私有物理页 #99："Yello"
B ------> 文件页 #42：    "Hello"
```

因此：

- `MAP_SHARED`：修改共享页，其他映射可以看到，脏页可以写回文件；
- `MAP_PRIVATE`：写入时复制，只有写入进程看到私有修改，原文件不变。

## 8. mmap 不只可以映射文件

`mmap` 也能创建匿名映射：

```c
mmap(NULL, size, PROT_READ | PROT_WRITE,
     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
```

匿名映射没有对应文件，常用于：

- 分配大块内存；
- 线程栈；
- 进程堆的部分实现；
- 共享内存；
- JIT 代码区域。

因此，更完整的定义是：

> `mmap` 在进程的虚拟地址空间中创建一段映射；这段映射的后备存储可以是文件，也可以是匿名内存。

## 9. 多进程共享不等于并发安全

两个进程映射同一个物理页，只解决了“双方能够看到同一批字节”，没有自动解决并发安全问题。多个进程同时修改共享数据时，仍然可能需要：

- 文件锁；
- 进程共享互斥量；
- 原子操作；
- 内存屏障；
- 明确的数据发布协议。

页面是共享的，不代表由多个字段组成的数据结构可以被另一个进程原子地观察到。

## 10. Java 中的 mmap

Java NIO 通过 `FileChannel.map()` 提供文件映射：

```java
try (FileChannel channel = FileChannel.open(path, StandardOpenOption.READ)) {
    MappedByteBuffer buffer =
            channel.map(FileChannel.MapMode.READ_ONLY, 0, channel.size());

    byte value = buffer.get(8192);
}
```

这里的 `MappedByteBuffer` 不是普通 Java 堆数组。它背后对应一段文件映射的虚拟地址空间。

常见模式包括：

- `READ_ONLY`：只读映射；
- `READ_WRITE`：可写的共享文件映射；
- `PRIVATE`：写时复制，修改不写回原文件；
- `force()`：请求把映射中的修改写回存储设备。

本仓库的最小示例位于：

- `nio/src/main/java/yier/bubu/nio/MappedFileDemo.java`
- `nio/src/test/java/yier/bubu/nio/MappedFileDemoTest.java`

## 11. 一个容易忽略的危险

如果建立文件映射后，文件被截短：

```text
原来映射：0 ～ 1 MiB
文件截短：只剩 4 KiB
程序访问：第 100 KiB
```

这不是普通的数组越界。Unix 系统上，访问已经超出文件当前范围的映射页可能触发 `SIGBUS`，导致进程退出。

因此，映射文件时必须控制文件大小和文件生命周期。

## 12. 最后总结

`mmap` 不是“把文件读进内存”的函数。它是：

> 在进程的虚拟地址空间中建立一段地址映射，让 CPU 对这些地址的普通内存访问，由操作系统按需转换成对文件页或匿名内存页的访问。

文件映射的基本过程是：

```text
mmap 建立地址关系
        |
        v
程序访问虚拟地址
        |
        v
缺页时由内核装入对应页面
        |
        v
页表指向物理内存
        |
        v
后续像普通内存一样访问
```

多进程共享映射的核心是：

> 各个进程通过自己的页表，把各自的虚拟地址映射到同一个 page cache 物理页。
