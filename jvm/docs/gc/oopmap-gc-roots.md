# HotSpot OopMap 与 GC Roots

本文整理一次关于 HotSpot OopMap、准确式垃圾收集和 GC Roots 的问答。

核心结论：

- **OopMap 记录的不是所有堆对象，而是某些执行位置上，栈和寄存器中哪些位置存放着对象引用。**
- **GC 不只扫描线程栈和寄存器，它还要枚举其他 GC Roots。**
- **线程栈和寄存器最难准确扫描，因为 JIT 编译后引用位置会随执行点变化。**
- **静态字段、JNI 引用、类加载器、锁对象、JVM 内部引用等通常由 JVM 自己维护的数据结构管理，相对更容易枚举。**
- **并发可达性分析的核心难点，是 GC 遍历对象图时用户线程还在修改引用，必须避免把活对象漏标成垃圾。**

---

## 1. 原文大意

现代主流 JVM 通常采用**准确式垃圾收集**。这意味着 JVM 在 GC 时需要准确知道哪些位置保存的是对象引用，哪些只是普通整数、浮点数或其他非引用数据。

当用户线程停顿下来以后，HotSpot 不需要把所有执行上下文、方法区或全局位置都逐个扫描一遍再猜测哪些值是对象引用。它会提前维护一些结构，用来告诉 GC：

```text
这里是对象引用
那里不是对象引用
```

HotSpot 中用于描述这些信息的重要结构之一就是 **OopMap**。

在类加载完成时，HotSpot 会计算对象内部哪些偏移量上是什么类型的数据，例如哪些字段是引用字段。即时编译过程中，HotSpot 也会在特定执行位置记录栈和寄存器里哪些位置是对象引用。

这样 GC 扫描时可以直接读取这些信息，不必从所有可能位置逐个检查。

---

## 2. OopMap 不是堆对象登记表

不能把 OopMap 理解成：

```text
OopMap = 所有堆对象的登记表
```

更准确的理解是：

```text
OopMap = 某个执行点上，栈和寄存器中对象引用位置的地图
```

例如：

```java
Object a = new Object();
int b = 123;
Object c = new Object();
```

某一时刻线程栈里可能有几个槽位：

```text
slot 0 -> a 的引用
slot 1 -> int 123
slot 2 -> c 的引用
```

OopMap 记录的是：

```text
slot 0 是对象引用
slot 2 是对象引用
```

它不是记录：

```text
堆里有对象 A
堆里有对象 C
```

GC 真正需要的是从 **GC Roots** 出发找到活对象。OopMap 的作用，是帮助 JVM 在扫描线程栈和寄存器这类 GC Roots 时，快速、准确地知道哪些位置保存着对象引用。

---

## 3. GC Roots 不只有栈和寄存器

只查找线程栈和寄存器里的引用是不够的。它们只是 GC Roots 的一部分。

常见 GC Roots 包括：

- **Java 线程栈中的引用**：局部变量表、操作数栈里的对象引用。
- **寄存器中的引用**：JIT 编译后的机器码执行时，对象引用可能保存在 CPU 寄存器里。
- **静态字段引用**：例如 `static Object obj`，只要对应类还活着，这个静态字段引用的对象就可能是根对象可达的。
- **JNI 引用**：Native 方法通过 JNI 持有的 Java 对象引用。
- **同步锁持有的对象**：例如某个对象正在作为 monitor 被 `synchronized` 使用。
- **JVM 内部数据结构持有的引用**：例如系统类加载器、运行时管理结构等。

整体过程可以简化成：

```text
GC Roots
  ├─ 线程栈里的引用
  ├─ 寄存器里的引用
  ├─ 静态字段引用
  ├─ JNI 引用
  ├─ JVM 内部引用
  └─ 其他运行时根引用
        ↓
    找到堆中的活对象
        ↓
    继续扫描这些对象内部的引用字段
        ↓
    找到更多活对象
```

所以 OopMap 不是说 GC 只看线程栈和寄存器，而是说：

```text
扫描栈和寄存器这一类 GC Roots 时，HotSpot 可以借助 OopMap 快速准确定位引用。
```

其他 GC Roots，例如静态变量、JNI 引用、JVM 内部句柄等，也会被 JVM 通过各自的运行时数据结构枚举出来。

---

## 4. 为什么栈和寄存器更难找

除了线程栈和寄存器，很多 GC Roots 通常更“有组织”，因为它们存放在 JVM 自己维护的数据结构里。

例如：

- **静态字段**：类元数据里知道哪些 `static` 字段是引用类型。
- **JNI 引用**：JNI local/global reference 本来就登记在 JVM 的句柄表里。
- **类加载器引用**：JVM 有对应的类加载器与类元数据管理结构。
- **同步锁对象**：对象监视器、锁记录等由 JVM 运行时结构维护。
- **JVM 内部引用**：VM 自己创建和管理，通常在固定的数据结构中。

线程栈和寄存器更复杂，因为它们的内容会随着程序执行不断变化：

```text
某一时刻：
  栈槽 1 是 Object 引用
  栈槽 2 是 int
  寄存器 rax 是对象引用

下一段代码：
  栈槽 1 可能复用了，变成 int
  rax 可能变成普通计算结果
```

JIT 编译后，变量也不一定老老实实待在解释器的局部变量表里，可能被优化到寄存器、栈槽或其他临时位置中。因此 HotSpot 必须在特定执行位置记录引用分布，这就是 OopMap 的价值。

“相对更好找”不等于“实现简单”。静态字段、JNI、类加载器、锁、运行时内部引用也有复杂的管理逻辑，只是它们不像线程栈和寄存器那样，需要在每个安全点精确描述“此刻哪里是引用”。

## 5. 并发的可达性分析为什么难

从 GC Roots 出发继续扫描对象图，是追踪式垃圾收集器判断对象是否存活的核心步骤。最容易理解的做法是暂停所有用户线程，让对象图在扫描期间保持不变：

```text
GC Roots
  ↓
活对象 A
  ↓
活对象 B
  ↓
活对象 C
```

这样 GC 只要顺着引用链遍历即可。问题在于，堆越大、活对象越多、对象之间引用关系越复杂，这个遍历过程越久。如果整个标记阶段都 Stop The World，停顿时间就会随堆规模增长。

并发标记想解决的就是这个问题：让 GC 线程和用户线程同时运行。但这也带来新的正确性问题：

```text
GC 正在标记对象是否存活
用户线程正在创建、删除、覆盖对象引用
```

如果 GC 把原本已经不可达的对象误标成存活对象，后果还能接受。这类对象叫浮动垃圾，本次没清掉，下次 GC 还能清掉。

真正不能接受的是另一种情况：**对象明明还活着，却被 GC 漏标成垃圾**。一旦这个对象被回收，用户线程后续再访问它，程序就会出错。

### 5.1 三色标记

三色标记是一种用来理解并发标记正确性的模型。它把对象分成三类：

- **白色**：GC 还没访问过。标记结束后仍然是白色，表示不可达，可以回收。
- **灰色**：GC 已经访问过这个对象，但这个对象引用的其他对象还没全部扫描。
- **黑色**：GC 已经访问过这个对象，并且这个对象引用的其他对象也都扫描完了。

可以把扫描过程想成一层波纹：

```text
黑色区域：已经扫完
灰色区域：正在推进
白色区域：还没扫到
```

如果用户线程暂停，灰色波纹一路向外推进，不会有歧义。并发时，用户线程会修改引用关系，对象图可能在扫描过程中发生变化。

### 5.2 对象消失问题

假设某个时刻对象颜色和引用关系如下：

```text
Root -> A(灰) -> C(白)

Root -> B(黑)
```

含义是：

- `A` 已经被 GC 访问过，但 `A` 的引用还没全部扫描完。
- `B` 已经被 GC 扫描完，GC 不会再回头扫描 `B`。
- `C` 还没被 GC 访问，所以还是白色。

这时用户线程并发执行了两次引用修改：

```java
B.ref = C;     // 黑色对象 B 新增了到白色对象 C 的引用
A.ref = null;  // 灰色对象 A 删除了到 C 的引用
```

修改后的真实对象图变成：

```text
Root -> B(黑) -> C(白)
```

`C` 明明仍然可以从 Root 到达，所以它应该存活。但对 GC 来说：

- `B` 已经是黑色，GC 认为它扫描完了，不会再重新扫描 `B.ref`。
- `A -> C` 这条还没扫描到的旧路径已经被删掉。
- `C` 可能一直保持白色，最终被误认为不可达。

这就是并发标记里的“对象消失”问题：对象没有真的消失，只是从 GC 的扫描视角里消失了。

这个致命问题需要两个条件同时满足：

- **黑色对象新增了到白色对象的引用。**
- **灰色对象删除了到这个白色对象的所有可达路径。**

只要破坏其中任意一个条件，就可以避免把活对象漏标成垃圾。

### 5.3 增量更新

增量更新破坏第一个条件：**不允许黑色对象悄悄新增到白色对象的引用。**

当用户线程执行类似操作时：

```java
B.ref = C;
```

如果 `B` 是黑色对象，`C` 是白色对象，JVM 会通过写屏障把这次新增引用记录下来。并发标记结束后，GC 会从这些记录过的黑色对象重新扫描一次。

可以简化理解为：

```text
黑色对象一旦新增指向白色对象的引用，就把这个黑色对象重新当成灰色对象处理。
```

CMS 的并发标记采用的是这个思路。

### 5.4 原始快照 SATB

原始快照（Snapshot At The Beginning，SATB）破坏第二个条件：**不允许通往白色对象的旧路径悄悄消失。**

当用户线程执行类似操作时：

```java
A.ref = null;
```

如果 `A.ref` 原来指向 `C`，JVM 会通过写屏障把这个被删除的旧引用记录下来。即使用户线程已经把 `A -> C` 删除了，GC 仍然可以按照“标记刚开始那一刻”的对象图继续扫描 `C`。

可以简化理解为：

```text
标记开始时能到达的对象，先按原始快照认为它应该被看见。
```

G1 和 Shenandoah 的并发标记采用的是这个思路。

### 5.5 写屏障的作用

这里的写屏障可以理解为 JVM 插在引用写操作旁边的一小段记录逻辑。用户代码看起来只是普通赋值：

```java
obj.field = newValue;
```

JVM 实际会在这类引用更新前后做一些额外处理：

```java
recordIfNeeded(obj.field, newValue);
obj.field = newValue;
```

增量更新记录的是“新增了什么引用”，SATB 记录的是“删除或覆盖前的旧引用”。两者目标相同：让并发标记在对象图不断变化时，仍然不会漏掉活对象。

## 6. 一句话总结

OopMap 是 HotSpot 为准确式 GC 准备的“引用位置地图”。它主要告诉 GC：在某个安全点，线程栈和寄存器中哪些位置保存着对象引用。GC 仍然要枚举所有类型的 GC Roots，再从这些根引用出发遍历堆中的活对象。

并发可达性分析进一步解决的是：从 GC Roots 往下遍历对象图时，如何让标记阶段和用户线程一起运行。它的底线是不能漏标活对象；多标出一点浮动垃圾可以接受，误回收活对象不可以接受。
