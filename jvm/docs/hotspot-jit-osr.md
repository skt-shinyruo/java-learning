# HotSpot JIT 与 OSR

HotSpot 判断“热点代码”时，常见来源有两类：

- 被频繁调用的方法。
- 被反复执行的循环体。

第一类很好理解：方法调用次数多，方法体自然执行得多。第二类解决的是另一种场景：一个方法可能只被调用一次或少数几次，但方法内部有一个执行次数很高的循环，循环体同样会成为热点。

## 1. 为什么热点循环也编译整个方法

即使热点只出现在方法中的某个循环里，HotSpot 的即时编译目标通常仍然是整个方法，而不是把循环体单独拿出来编译成一个独立对象。

原因是编译器需要看到方法级别的信息：

- 局部变量表和操作数栈在不同字节码位置的状态。
- 循环前后的控制流关系。
- 异常处理、同步块、返回路径等方法级结构。
- 后续去优化时如何恢复成等价的解释器栈帧。

差别在入口位置。普通 JIT 编译通常从方法开头进入；OSR 编译会带着一个执行入口的字节码序号，也就是 BCI（Byte Code Index），让编译后的代码可以从循环附近的某个字节码位置进入。

## 2. OSR 是什么

OSR 是 On-Stack Replacement，通常翻译为“栈上替换”。

它表达的是：方法还没有执行完，当前方法的栈帧还在虚拟机栈上，JVM 就把这次正在执行的方法从解释执行切换到编译后的机器码继续执行。

例如：

```java
void work() {
    int sum = 0;

    for (int i = 0; i < 100_000_000; i++) {
        sum += i;
    }

    System.out.println(sum);
}
```

如果 `work()` 只调用一次，普通方法调用计数未必足够触发方法级编译。但循环回边会反复执行，回边计数足够高后，HotSpot 可以触发 `work()` 的 OSR 编译。

这里的“回边”可以粗略理解为循环末尾跳回循环开头的那条控制流：

```text
i++
if (i < 100_000_000) goto loopStart
```

## 3. 正在执行的方法如何切换

OSR 不是在任意机器指令中间强行打断 Java 代码。切换发生在 HotSpot 能准确描述程序状态的执行点上，常见位置就是解释器执行循环回边或循环入口附近的字节码边界。

到达这个位置时，JVM 能知道当前解释器栈帧里的状态：

```text
当前方法：work
当前 BCI：循环入口或回边对应的位置

局部变量表：
  sum = 123456
  i   = 789

操作数栈：
  在该字节码位置有明确的栈形态
```

如果 OSR 编译结果还没有准备好，默认情况下执行线程通常继续按解释方式运行，编译线程在后台完成编译。等后续再次到达合适的循环检查点时，解释器可以发现已有可用的 OSR 版本，然后进入编译后的代码。

如果 OSR 编译结果已经可用，切换过程可以理解为：

```text
解释器执行 work()
  -> 到达循环回边，发现存在可用的 OSR 编译版本
  -> 根据当前解释器栈帧提取局部变量、操作数栈和锁等状态
  -> 按 OSR 入口需要的格式迁移这些状态
  -> 跳入 work@某个BCI 的编译后机器码
  -> 从 i = 789、sum = 123456 这样的当前状态继续执行
```

所以 JVM 不是把 `work()` 停掉后从方法开头重新执行，也不是丢弃当前循环进度。它是在一个可恢复、可描述的字节码边界，把解释器帧中的执行状态迁移到编译代码所需的栈槽或寄存器布局中，然后跳到编译代码的 OSR 入口继续跑。

## 4. 为什么能继续而不是重来

能继续执行的关键是：字节码执行模型在每个重要位置都有明确的“帧状态”。

帧状态包括：

- 当前执行到哪个 BCI。
- 每个局部变量槽里的值。
- 操作数栈上的值和类型。
- 当前持有的锁或同步块状态。

OSR 编译时，编译器会针对指定 BCI 生成一个特殊入口。这个入口不要求从方法第一条字节码开始，也不要求重新初始化 `sum` 和 `i`；它接收的是当前解释执行已经得到的状态。

对于上面的例子，切换前后更接近这样：

```text
解释器：
  i = 789
  sum = 123456

OSR 切换：
  把 i、sum 等状态放到编译代码期望的位置

编译代码：
  从 i = 789 继续执行后续循环
```

## 5. 和去优化的关系

JIT 为了性能可能会做一些基于运行时观察的优化，例如类型预测、内联、消除某些检查。OSR 进入编译代码后，如果这些优化假设后来不成立，HotSpot 还可以执行反向操作：从编译代码退回解释器继续执行。

这个过程叫去优化（deoptimization）。它同样依赖编译代码保存的调试信息和帧状态：JVM 需要知道如何把寄存器、栈槽中的值还原成解释器能理解的局部变量表和操作数栈。

因此，OSR 和去优化可以放在一起理解：

- OSR：解释器栈帧还在执行中，切到编译代码继续执行。
- 去优化：编译代码中的优化假设失效，还原出解释器栈帧继续执行。

两者都要求 JVM 能在特定执行点精确描述 Java 层面的栈帧状态。
