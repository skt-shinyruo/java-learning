# HotSpot OopMap 与 GC Roots

本文整理一次关于 HotSpot OopMap、准确式垃圾收集和 GC Roots 的问答。

核心结论：

- **OopMap 记录的不是所有堆对象，而是某些执行位置上，栈和寄存器中哪些位置存放着对象引用。**
- **GC 不只扫描线程栈和寄存器，它还要枚举其他 GC Roots。**
- **线程栈和寄存器最难准确扫描，因为 JIT 编译后引用位置会随执行点变化。**
- **静态字段、JNI 引用、类加载器、锁对象、JVM 内部引用等通常由 JVM 自己维护的数据结构管理，相对更容易枚举。**

---

## 1. 原文大意

现代主流 JVM 通常采用**准确式垃圾收集**。这意味着 JVM 在 GC 时需要准确知道哪些位置保存的是对象引用，哪些只是普通整数、浮点数或其他非引用数据。

当用户线程停顿下来以后，HotSpot 不需要把所有执行上下文、方法区或全局位置都逐个扫描一遍再猜测哪些值是对象引用。它会提前维护一些结构，用来告诉 GC：

```text
这里是对象引用
那里不是对象引用
```

HotSpot 中用于描述这些信息的重要结构之一就是 **OopMap**。

在类加载完成时，HotSpot 会计算对象内部哪些偏移量上是什么类型的数据，例如哪些字段是引用字段。即时编译过程中，HotSpot 也会在特定执行位置记录栈和寄存器里哪些位置是对象引用。

这样 GC 扫描时可以直接读取这些信息，不必从所有可能位置逐个检查。

---

## 2. OopMap 不是堆对象登记表

不能把 OopMap 理解成：

```text
OopMap = 所有堆对象的登记表
```

更准确的理解是：

```text
OopMap = 某个执行点上，栈和寄存器中对象引用位置的地图
```

例如：

```java
Object a = new Object();
int b = 123;
Object c = new Object();
```

某一时刻线程栈里可能有几个槽位：

```text
slot 0 -> a 的引用
slot 1 -> int 123
slot 2 -> c 的引用
```

OopMap 记录的是：

```text
slot 0 是对象引用
slot 2 是对象引用
```

它不是记录：

```text
堆里有对象 A
堆里有对象 C
```

GC 真正需要的是从 **GC Roots** 出发找到活对象。OopMap 的作用，是帮助 JVM 在扫描线程栈和寄存器这类 GC Roots 时，快速、准确地知道哪些位置保存着对象引用。

---

## 3. GC Roots 不只有栈和寄存器

只查找线程栈和寄存器里的引用是不够的。它们只是 GC Roots 的一部分。

常见 GC Roots 包括：

- **Java 线程栈中的引用**：局部变量表、操作数栈里的对象引用。
- **寄存器中的引用**：JIT 编译后的机器码执行时，对象引用可能保存在 CPU 寄存器里。
- **静态字段引用**：例如 `static Object obj`，只要对应类还活着，这个静态字段引用的对象就可能是根对象可达的。
- **JNI 引用**：Native 方法通过 JNI 持有的 Java 对象引用。
- **同步锁持有的对象**：例如某个对象正在作为 monitor 被 `synchronized` 使用。
- **JVM 内部数据结构持有的引用**：例如系统类加载器、运行时管理结构等。

整体过程可以简化成：

```text
GC Roots
  ├─ 线程栈里的引用
  ├─ 寄存器里的引用
  ├─ 静态字段引用
  ├─ JNI 引用
  ├─ JVM 内部引用
  └─ 其他运行时根引用
        ↓
    找到堆中的活对象
        ↓
    继续扫描这些对象内部的引用字段
        ↓
    找到更多活对象
```

所以 OopMap 不是说 GC 只看线程栈和寄存器，而是说：

```text
扫描栈和寄存器这一类 GC Roots 时，HotSpot 可以借助 OopMap 快速准确定位引用。
```

其他 GC Roots，例如静态变量、JNI 引用、JVM 内部句柄等，也会被 JVM 通过各自的运行时数据结构枚举出来。

---

## 4. 为什么栈和寄存器更难找

除了线程栈和寄存器，很多 GC Roots 通常更“有组织”，因为它们存放在 JVM 自己维护的数据结构里。

例如：

- **静态字段**：类元数据里知道哪些 `static` 字段是引用类型。
- **JNI 引用**：JNI local/global reference 本来就登记在 JVM 的句柄表里。
- **类加载器引用**：JVM 有对应的类加载器与类元数据管理结构。
- **同步锁对象**：对象监视器、锁记录等由 JVM 运行时结构维护。
- **JVM 内部引用**：VM 自己创建和管理，通常在固定的数据结构中。

线程栈和寄存器更复杂，因为它们的内容会随着程序执行不断变化：

```text
某一时刻：
  栈槽 1 是 Object 引用
  栈槽 2 是 int
  寄存器 rax 是对象引用

下一段代码：
  栈槽 1 可能复用了，变成 int
  rax 可能变成普通计算结果
```

JIT 编译后，变量也不一定老老实实待在解释器的局部变量表里，可能被优化到寄存器、栈槽或其他临时位置中。因此 HotSpot 必须在特定执行位置记录引用分布，这就是 OopMap 的价值。

“相对更好找”不等于“实现简单”。静态字段、JNI、类加载器、锁、运行时内部引用也有复杂的管理逻辑，只是它们不像线程栈和寄存器那样，需要在每个安全点精确描述“此刻哪里是引用”。

---

## 5. 一句话总结

OopMap 是 HotSpot 为准确式 GC 准备的“引用位置地图”。它主要告诉 GC：在某个安全点，线程栈和寄存器中哪些位置保存着对象引用。GC 仍然要枚举所有类型的 GC Roots，再从这些根引用出发遍历堆中的活对象。
